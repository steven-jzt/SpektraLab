# 从 Shayt0ny/Spektra-Studio 身上学什么

对照对象：`Shayt0ny/Spektra-Studio`（★79，1.3.4-win.2 → win.9 / Studio 1.0.10，2026-10-29 建仓）
基线：官方 `Windows_Linux` @ aaec952（我们的构建）

---

## 一、先说结论：哪些**不值得**学

**1. （已纠正）"中文路径起不来"不是中文的问题，是目录 ACL 的问题**

原先我判定"官方包和社区包在中文路径下都失败"，**这个结论是错的**，已用干净的
`C:\Users\steve\中文测试` 目录推翻：官方 aaec952 与他们的 win.6 在中文目录里都能正常启动。

真凶是某个目录上继承的异常 ACL：

```
Everyone:(CI)(DENY)(DC)                 ← 拒绝删除子项
S-1-4-450123902-439756660:(OI)(CI)(W,D,DC)
```

`C:\Users\steve\Desktop\胶片模拟程序` 就带这条 ACE。放在它下面的任何 SpektraLab 副本
（官方、社区、自建）都会在 WebView2 建环境阶段失败，且错误码会漂移：
`os error 5` / `0x800700AA`（资源在使用中）/ `0x8000FFFF`（灾难性故障）。
把同一批文件拷到该目录之外，立刻正常。

所以他们那条"中文安装路径"修复（`edge_raster.cpp` 里字体 `fopen` → `_wfopen`）
解决的是**引擎字体加载**那一层（症状 `cannot load the font for HelveticaNeue`），
和我们撞到的外壳层 WebView2 失败无关，也不是虚假宣传。教训：在带自定义 ACL
的目录里做启动排障，会得出完全错误的结论。

**2. AI 调色建议 / Spektra Studio 品牌**——已经是另一个产品，且他们自己也写明"只发文本与统计，不看图"。

**3. DCP / LCP / 候选 RAW 解码器**——价值高但工作量是"再造半个解码栈"，且依赖 Adobe 私有配置，不适合作为对齐上游的第一步。

## 二、值得学的，按性价比排序

### A 档：小改动、明确收益、可独立 cherry-pick

1. **避免二次高光压缩**（win.5/6）
   症状具体：灰阶测试里白色输出约 228 而不是 255。属于渲染正确性 bug，不是口味问题。
   落点：`engine/src/pipeline/` 的输出/显示变换链。

2. **Post-Dev 调整统一在 ProPhoto 工作空间**
   现状问题：调色工作空间可能随导出方案变化。修好后"预览与导出同源"，这恰好也是 macOS 那边的设计意图。
   落点：`pipeline.cpp` 的 post-dev 阶段 + `output_transform` 调用点。

3. **16-bit 原图预览传输与精度协商**
   减少渐变在预览阶段的提前量化。我们的日志里 `original_thumbnail_pending` 就是这条链。
   落点：`host/output.cpp` 传输格式 + `glRenderer.ts` 的 `uOriginal16` 路径。

4. **16 位预览缩图的未定义导数问题**
   他们写得很具体：导数在像素条件分支之后读取 → 改为分支前计算。这是典型的 GLSL 精度陷阱，改动极小。

### B 档：中等工作量，但要先想清楚产品边界

5. **多选导入**（拖入后弹窗勾选，确认前不解码）
   纯 UI 层，`desktop/src/windows/`。对"一次导入一文件夹"的用法提升明显，风险低。

6. **一键自动调整**（win.8）
   他们的设计值得抄的是**约束**，不是算法：只读长边 ≤512 的原生小预览、每次先归零避免累积、单步撤销、过期结果不覆盖、样本不足不强行调整、±1.2 EV 上限。
   落点：`desktop/src/shared/` + `state/session-*`。

7. **WebGL 上下文丢失自动重建**
   我们的 `glRenderer.ts` 有 `uOriginal` 等纹理状态，丢上下文后不重建就是黑屏。他们做的是"重建画布 + 恢复期缩小显示纹理"，不影响导出分辨率。

### C 档：大工程，但能解释我们遇到过的一半怪现象

8. **显存/UMA 预算与回收**（win.7）
   "本地显存不足时先回收空闲缓存，再走驱动允许的共享堆，并保留预算与 commit 检查"。这台机器是 Intel Arc 核显（UMA），这条对我们直接相关。

9. **导出冻结相机/镜头配置，独立解码**
   避免导出时误用编辑会话的旧 decode 设置。属于正确性问题。

## 三、方法论上更值得学的（比代码更值钱）

1. **每个版本一份 notes + `FILES.sha256` + `VALIDATION.txt`**
   他们每版都写清"做了什么/没验证什么/边界在哪"，例如"780M 的问题来自其他用户，本机只做了模拟内存布局验证"。这种诚实标注让下游能判断可信度。

2. **把"复现步骤"写进文档**
   `WINDOWS_UNICODE_FONT_HOTFIX.md` 直接给了根因（UTF-8 路径传给窄字符 `fopen`）、复现目录（含"柯达"）、验证方式（新增 `host_unicode_resources.py`）。这是可以直接照抄的工程习惯。

3. **用真实 RAW 做门禁**
   他们验证用了 2500 万像素真实 RAW、7168×10240 全尺寸渲染。我们目前只有合成 PNG 的端到端。

## 三·五、实测后的修正（2026-11-05 晚，按 git blob 哈希比对）

拿他们的 `main` 与我们的树逐文件比 blob 哈希（范围 engine/src、engine/host、desktop/src）：

```
完全一致   214 个
有差异      59 个
仅他们有   108 个
```

引擎侧：**19 个文件被改**（`pipeline.cpp` 125 KB、`engine.cpp` 156 KB、`host/main.cpp` 95 KB、
`vulkan_gpu.cpp` 71 KB、`params.*`、`raw_decoder.cpp`、`lens_correction.cpp` …），
另有 **28 个新文件**（`edge_raster.cpp`、`spk_mask_reduce/epilogue.comp`、
`spk_overscan_common.glsl`、`spk_view_decorations/detail/film_mix.comp`、
`vulkan_memory.hpp`、`raw_profile.cpp`、`raw_candidate_*.cpp`、`local_masks.hpp` …）。

结论要改写：**他们不是"打了补丁"，是重写了 Windows 引擎的一层**。所以"挑几个补丁
cherry-pick"基本不成立——举个例子，`view.hpp` 只加了 `bool rgba16 = false` 参数并改了
显示染色映射的注释语义，但配套改动散在 pipeline / engine / host / output / glRenderer 五处，
单独挑一个文件没有意义。

另外：他们的 `spk_mask_*` 内核已经写出来了，但 `capabilities` 里 `contrast_mask` 仍然被拒
（我实测过 win.6 的 host），说明他们也在守"上游隐藏"的边界。

因此下面这段"合并顺序"只在**自己实现**的前提下成立，不适用于搬他们的代码。

## 四、若要合并，建议的顺序

1. 高光压缩 + Post-Dev 空间（正确性，先做）
2. 16-bit 预览链 + 缩图导数（画质可见）
3. WebGL 恢复（稳定性）
4. 多选导入 / 一键自动调整（体验）
5. 显存预算（工程量大，但核显受益明显）

前两条必须先跑 `spk_render_fixture` 类的像素门禁，否则等于在没有护栏的情况下改渲染。
